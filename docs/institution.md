# Institution collections and versioned API

The version1 institution routes are connected to the existing authenticated API. Actual HTTP/PostgreSQL qualification passed for collection import, scoped access, stable pagination, rollback, optional metadata and rights-preserving export. This feature maps institution inventory metadata onto **existing authorized artworks**; binary artwork import remains the existing CMS/import/OES workflow. It does not fabricate assets, approval, or provenance.

`org.exhibitos/institution` is an ordinary existing OES extension object with version1, collectionId, accessionNumber, classification, optional acquisitionYear, preservationStatus and bounded dated history. Optional bibliography contains at most32 references of1024 characters; distinct exhibitionHistory and conservationHistory each contain at most16 closed year/description entries. Existing records without these optional fields remain compatible. Institution custody/history is separate from artwork ownership, permissions and software licensing. Preservation completeness is not an artist quality score. Contact fields and unknown fields are rejected. Do not put personal information in free-text descriptions. API responses omit issuer/user IDs and private token hashes.

An authenticated tenant admin creates a collection and issues an opaque token once. PostgreSQL retains only its SHA256, explicit read/write/export scopes, collection IDs and artwork IDs (each maximum100), expiry (60–86400 seconds), revocation and authenticated-request quota (60/minute, including rejected scoped operations). Every bearer operation resolves the issuer's **current** admin membership, disabled status and current artwork access. Foreign tenant, collection or artwork IDs cannot be admitted by possession of a token alone. Export additionally checks current artwork export rights. There is no wildcard token. Write/export tokens also require read scope for receipt and inventory inspection. Tokens must be handled as credentials: never place them in command arguments, URLs, logs or Git.

Inventory import accepts maximum100 rows/256KiB into a maximum1000-record collection. Each row is checked within a PostgreSQL savepoint. Invalid rows produce bounded index/state/code results without leaking row contents; valid rows commit together with immutable inventory and history. A durable request ID + canonical payload digest reopens the same result, and conflicting reuse fails. Batch status exposes processed/total and per-row results. Explicit rollback only deactivates records from that batch, appends honest history and preserves the batch/original inventory; it never deletes the source artwork or rewrites its rights. Rolled-back batches reopen as rolled-back rather than replaying the import.

Pagination/filter snapshots are PostgreSQL-backed, tenant/user/collection/filter-bound and expire after15 minutes. Cursor continuation preserves the captured inventory rows across later inserts/rollbacks, with current artwork access checked again before each returned page. Maximum100 records/page. Expired cursor records remain retained pending the separate retention task; expiry refuses their use. Export uses the same cursor and produces institution extension mappings plus the current artwork rights record, including its copyright holder and creditLine, without private artwork bytes. Institution fields never overwrite that rights record. Rights revocation still refuses export.

## HTTP integration contract

Existing cookie/CSRF Auth.request wraps admin collection/token operations. Cookie inventory/export calls also use a **mutating transaction** because pagination stores a cursor snapshot. Bearer calls use Institution.request with the existing auth and maintenance advisory locks; the current issuer membership supplies authority. Connected routes enforce the configured host/origin and existing bounded error responses. Version1 routes below share the prefix `/api/v1/tenants/:tenantId/institution`; use your actual authorized tenant ID:

- POST `/api/v1/tenants/:tenantId/institution/collections` {name}
- POST `/api/v1/tenants/:tenantId/institution/tokens` {scopes,collections,artworks,seconds}; response token returned once; POST `tokens/:id/revoke`
- POST `collections/:id/import` {requestId,rows:[{artworkId,metadata}]}
- GET `collections/:id/batches/:batchId`; POST same path `/rollback`
- GET `collections/:id/inventory` and `/export` with cursor/filter/limit
- GET `collections/:id/inventory/:inventoryId/history`

Collection creation, token issuance and revocation require an authenticated admin session with the existing CSRF header. Inventory/import/export/batch/history routes accept that session or an explicitly scoped bearer in the Authorization header. A bearer cannot issue further tokens. The route contract is documented in `contracts/institution-openapi.json`; migrations011 and012 are additive, and migration001–010 remain unchanged. Migration-aware whole-service backup qualification remains a separate task.

## Education assignment and guided tour

Use an API client that stores credentials privately and sends the existing session cookie, CSRF header and configured Origin. Replace the named IDs below with IDs returned by your own tenant; never put a token in a URL or command argument.

1. In the existing CMS/import workflow, choose two artworks you can access, complete their metadata and rights review, and retain their actual artwork IDs. For the tour, use an existing approved, published exhibition containing those works and copy its current public `/p/:publicationId` URL. Collection inventory does not publish artwork or grant model downloads.
2. As the tenant admin, POST the collection route with `{"name":"Museum learning set"}` and retain its returned collection ID. POST `collections/:collectionId/import` with a fresh UUID requestId and rows referring to those actual artwork IDs. Each row has artworkId and metadata. For example, the first metadata object can be `{"accessionNumber":"LEARNING-001","classification":"Sculpture","preservationStatus":"unknown","history":[{"year":2026,"description":"Added to the learning set"}],"bibliography":["Public collection catalogue"],"exhibitionHistory":[],"conservationHistory":[]}`. Give the second row a distinct accessionNumber. Retain the returned batch ID and inspect processed/total and each row's imported/rejected result before continuing. Reusing the same requestId with the same input retrieves the original receipt.
3. Issue an education-client token using `{"scopes":["read"],"collections":["<returned collection ID>"],"artworks":["<first actual artwork ID>","<second actual artwork ID>"],"seconds":3600}`. Store the once-returned credential privately and send it only as `Authorization: Bearer <token>` to this server. It grants access only to those collection/artwork IDs while the issuer remains authorized.
4. The education client GETs `collections/:collectionId/inventory?limit=1`, then repeats the request with the returned cursor until it is null. Keep the same filter when continuing; for example, `filter=LEARNING` selects matching accession numbers. Students record each accessionNumber, classification and one dated history observation, then compare these custody records with the artwork's existing title, artist and rights information. Explain why institution preservationStatus and collection history do not establish copyright ownership or software licensing.
5. Open the approved public exhibition URL for a guided tour. Ask students to locate both works, compare the visible work with the inventory labels and cite the public catalogue reference. A withdrawn exhibition or revoked rights must not be worked around using inventory credentials. No student names, email addresses or assessment results are added to institution metadata.
6. To correct a mistaken import, the admin POSTs `collections/:collectionId/batches/:batchId/rollback` with `{}`. Inspect the batch receipt and `inventory/:inventoryId/history`: the original imported record remains, and rolled-back history is appended. Only that batch's inventory mappings are deactivated; source artworks and their rights remain. Submit corrected rows with a new requestId. Revoke the education token through `tokens/:id/revoke` when the lesson ends.

If the lesson needs authorized extension mappings, issue a separate token with read and export scopes for the same exact IDs, then GET the collection export route. Export returns the current artwork rights alongside the institution extension, preserving copyright holder and creditLine; current export rights are rechecked. It does not export private model bytes.

Actual HTTP/PostgreSQL qualification passed for these API boundaries, including malformed-row partial progress, tenant/collection/artwork IDOR refusal, durable quota, cursor stability, batch rollback, revocation and optional metadata/rights export. This evidence covers the implemented API scenario; it does not claim a completed classroom trial or complete predecessor deployment/release gates or the whole institution task.
