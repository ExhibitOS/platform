# Painting resolution: producer boundary under review

This is a source-only design at Platform `6a9eee5deda7abd8e7034d92792208055c54357b` (tree `3fe8fce6b698706a7d6ad71c5acab1e5a8a66cc4`). It does not enable a larger image or establish an accepted resource budget.

## Current boundaries

* `prepared-image.ts` accepts a client-declared RGB8 preparation receipt, limits the encoded PNG to 8 MiB, and checks dimensions at 2048 per edge and 4,194,304 pixels. Settings and pixel hashes record provenance; they do not authorize a larger image or prove pixel equivalence.
* `derivative.ts` accepts 512 or 2048 as `maxTextureSize`; its worker has a 128 MiB heap setting and five-second timeout. `validation-worker.ts` admits those sizes and uses the strict PNG decoder, whose default is 4,194,304 pixels. The decoder verifies chunks, CRC, supported color data, bounded inflation and scanlines.
* `demo-display-derivative.ts` selects 2048 for ordinary primary images and 512 for coarse images. An exact approved image is checked against approval limits and decoded before clean bytes are reused; embedded watermarking uses the derivative path. Rights and current approval are checked by the existing caller.
* The existing display cache recipe includes source SHA, maximum texture size and watermark. It distinguishes derivative results; a cache key is not an authorization decision.
* Main owns `demo-display-policy.ts`, publication, approved pair qualification, OEX, shared contracts and Viewer loading. Current exact approval and Viewer loading still impose 2048 and other limits; changing only the producer cannot qualify an end-to-end larger image.

## Proposed boundary, not yet agreed

Main's existing approval path could return a narrowly scoped internal capability only after current revision, rights, source hash and byte count have been verified. A producer could consume that capability for an explicitly selected full image, with fixed reviewed edge, pixel and resource limits. No capability means the existing behavior. Arbitrary caller numbers, a client settings digest, an inventory claim or a cache hit must not grant admission. The exact type, scope, lifetime, caller and values require agreement with Main; the Manager preparation path needs its own trusted opt-in and matching receipt/capability negotiation.

If implemented, the selected limit and any additional behavior affecting output must be reflected in cache identity. Preview and coarse lanes remain separately bounded. Preserve the 8 MiB encoded bound, original bytes and rights, ICC evidence, strict decoding, no upscaling and existing 2048 compatibility. An exact-file approval must continue binding the actual bytes; watermarking cannot silently bypass its policy. Do not infer safe limits from the three artworks' target pixel counts.

## Evidence needed before choosing limits

Studio and Manager should agree on a synthetic measurement design covering boundary and over-boundary dimensions and pixels, encoded size at and over 8 MiB, RGB8 and supported alpha behavior, malformed chunks/CRC and compressed expansion, no-upscale and aspect ratio, ICC receipt/readback, unchanged default and watermark/cache separation. Measure worker wall time and peak memory, including decoded buffers and derivative output, under its actual process limit; test cancellation and failure without partial output. Main must separately establish publication/OEX and Viewer admission, selected-image decode, GPU maximum texture size, peak/resident/mipmap budgets and compact fallback. A passing synthetic result alone does not approve real artwork or public release.

Implementation waits for the agreed capability and bounded values, Manager input contract, Main consumer boundary and review of measurement evidence. Actual image conversion, exhibition edits, public output and deployment are outside this design unit.

## Synthetic decoder measurement

The test-only `apps/api/src/painting-decoder-measure.fixture.mjs` directly imports the unchanged decoder. Run once through the existing resource queue with Node 24: `node --experimental-strip-types apps/api/src/painting-decoder-measure.fixture.mjs <exact-head> <new-output-directory>`. It generates only the three agreed RGB8 sizes; the pattern repeats each row, with channels derived from the x coordinate and default zlib compression. It is not a worst-case image. Encoded input is limited to 8 MiB; decoded raw bytes are checked against the generated raw hash and expected scanline length, not limited to 8 MiB. The isolated child uses a 128 MiB V8 old-space limit, reports decoder elapsed time and separately measured process wall time and peak RSS. Five seconds is an observed decoder-time threshold, not a kill deadline. No new encoded output is produced by the decoder. The measurement does not qualify the production worker, Manager preparation or Viewer resources.

## Private native preparation receipt and capability

The internal candidate capability in draft Platform #384 is a dormant, exact-approval-bound contract. Manager's private preparation receipt identifies `recipeID: "native-private-demo-painting-rgb8"` and `recipeVersion: 1`; its `settingsSHA256` corresponds to the approval candidate's `recipeSha256`. The receipt's `image.outputWidth` and `image.outputHeight` correspond to the candidate's `sourceWidth` and `sourceHeight`: these describe the prepared PNG supplied to Platform, not the original JPEG dimensions. The original JPEG identity, dimensions and effective orientation remain in the separate Manager receipt. The fixed prepared PNG profiles are 1925 × 2634, 2419 × 2552 and 2135 × 1361. Manager's private recipe uses a common no-upscale factor, floor rounding on both axes and nearest-centre sampling; this differs from earlier synthetic Node measurements and does not imply identical bytes.

The approved candidate's `colour` is exactly one of:

* `{kind: "no-profile-srgb-assumed"}` for an explicitly established absence of an embedded profile, with sRGB assumed.
* `{kind: "icc-to-srgb", version: 1, algorithm: "icc-to-srgb-jpeg-rgb8-v1", sourceIccSha256: <digest>}` for the corresponding ICC conversion claim. Manager's image report spells the source ICC field `sourceICCSHA256`; the receipt's colour object and Platform candidate's colour object use `sourceIccSha256`.

Receipt consumers must compare the exact source and prepared PNG identities and bytes, dimensions, colour evidence, recipe ID/version, settings digest and other relevant receipt fields against reviewed evidence before any future admission. A missing profile field is not evidence that a profile is absent. Capability issuance validates the approved claim's shape and binds it, the recipe and prepared PNG to the cache identity; it does not independently verify the original JPEG, profile absence, conversion, settings or receipt. Nor does its PNG header/IHDR check replace strict full PNG decoding. No production approval currently grants this capability and there is no trusted CMS caller or high-resolution worker path. Real source review, rights and current CMS authorization, strict decoding and resource/Viewer validation remain prerequisites for a separate activation decision.

A subsequent source-only strict validator can consume an already-issued private capability: it rechecks the source-bound capability, uses a fixed-profile worker to validate the entire bounded RGB8 PNG with sRGB intent 0, and rechecks the capability after the worker closes. Cancellation and malformed inputs do not return a successful validation; worker transport and timeout failures remain distinguishable from malformed input. The PNG tag does not prove ICC conversion accuracy. This helper creates no asset and does not obtain a current CMS snapshot or first-import authority. A trusted caller must supply and recheck the actual CMS transaction context; the existing capability's approved-primary requirement makes it unsuitable as the authority for the first registration of that same PNG. That separate server-owned pre-admission boundary and its live tenant, artwork, rights and revision bindings remain unimplemented.
