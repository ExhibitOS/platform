# Technical preservation inventory

Preservation reports technical availability for the signed-in artwork owner or tenant administrator. It does not score an artist, rank works, infer artistic quality, grant display/export access or publish private provenance. The read-only inventory uses current tenant access and the normal policy/storage transaction fences; it creates no derivative, migration, backup or audit mutation.

The authenticated route is `GET /api/v1/tenants/:tenantId/cms/artworks/:artworkId/preservation`; integration retains existing session and no-store policy. `Preservation.inventory(client,session,artworkId)` returns immutable revision and approval hashes, observed source/derivative hashes and byte counts, current rights/provenance, implemented OES/OEX/hash profiles and explicit warnings. It never returns object keys, filesystem paths, media bytes or credentials. Rights booleans describe current metadata; they are not an export or viewing permit.

Each source and derivative is checked against actual retained byte size and SHA-256. Missing masters, mismatching bytes, unsupported media formats, invalid historical versions and unavailable rights receive separate warnings. A read/storage failure is reported as unavailable rather than a successful preservation result. Observation is bounded to 128 source files, 128 derivatives, 128 revisions and 64 MiB declared bytes per report. Incomplete observations remain unverified. Supported MIME recognition plus exact hashes is not a decoder or native format certification.

Original Capture, high-resolution masters, original texture, capture time/device and color profile remain `unknown`: the current Platform CMS schema does not independently establish those records. Physical dimensions indicate recorded metadata, not a new physical measurement. CMS upload/created timestamps are not capture dates. A verified web asset is not proof that original sensor data or a high-resolution original survives.

Keep the original artifact and its version/hash inventory. On missing bytes, recover an authorized matching master from the operator's verified backup; preserve damaged bytes and diagnostics until the exact replacement is checked. On hash mismatch, do not silently rewrite metadata to accept different bytes. Unsupported versions require an explicitly registered adapter or the original retained reader; never rename a version field to force acceptance.

For software disappearance or a historical renderer, use the retained signed runtime and [frozen reconstruction guide](freeze.md). Existing grants and expiry remain enforced; archival retention does not authorize indefinite display. An OEX export is an open artifact, not a complete database/blob/configuration backup. Legacy conversion and actual independent reconstruction are separately recorded T11-03 work; this inventory alone does not complete that task.

Explicit legacy conversion uses `migrateLegacyOex(input,{createdAt})`: supported draft.1 OEX is written as a new draft.2 package, preserving its scene, rights, provenance and exact asset bytes. The receipt binds both package hashes and the exhibition revision hash. Keep the original package; current or unknown versions are refused as conversion sources, and signed freezes are never rewritten.
